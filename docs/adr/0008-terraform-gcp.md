# ADR 0008 — Terraform-managed GCP foundation

- Decision: Use Terraform for an isolated bootstrap and split dev foundation/runtime states; define but never apply staging/prod in this iteration.
- Status: Accepted; apply externally blocked until open billing exists
- Context: Managed GCP services reduce initial operations, but manual resources would create drift.
- Alternatives: Manual console; Kubernetes; one broad Terraform root/identity; split Terraform foundation/runtime roots and phase identities.
- Evidence: Discovery shows zero visible organizations, six closed billing accounts and one billing-disabled exact-name candidate with unknown provenance and no Terraform adoption record.
- Chosen option: Terraform always manages distinct bootstrap/dev projects and Monitoring email channels through either creation or evidence-backed declarative import; required labels, verified delivery and foundation provenance are enforced before costly resources. A separately administered foundation owns APIs, IAM, registry, SQL, alert delivery and budget; a narrow runtime root owns private Cloud Run. Three fixed bootstrap WIF identities bind immutable GitHub owner/repository IDs plus exact names/workflow/ref/environment. Routine apply has 16 non-destructive Cloud Run permissions plus service-only invocation, repository read and a separate two-permission rollback-tag role. State locks remain releasable under versioning/soft delete; cleanup retains 20 recent versions plus the immediate predecessor while runtime images stay digest-bound; exact-plan attestation, cost, evidence and rollback gates remain mandatory.
- Trade-offs: Split states, three identities, custom state/Cloud Run/tag roles, explicit project/channel adoption and a one-digest rollback window add bootstrap/operator work. Plan still needs to create/delete Terraform's ephemeral runtime `.tflock`, but it cannot mutate `.tfstate`; apply can mutate only runtime state. The deployer can create or update one repository tag but cannot upload/delete artifacts or change repository policy. Managed services still incur ongoing cost.
- Consequences: No resource may target the unrelated configured project. Foundation changes require a separately authorized and reviewed plan. Routine apply accepts only the saved runtime plan whose hash, full tracked tree, commit, foundation-repository image, workflow, actor, independent reviewer and run URL match a fresh `ALLOW_DEV_APPLY` attestation verified before authentication. Only after attestation/auth/preflight may it revalidate and tag the immediate predecessor; deployment still uses the digest. Post-apply verifies named container provenance and live foundation authority. A real plan/apply still waits for billing and target authorization.
- Review trigger: Billing/parent selection, organization policy, measured workload, or a staging authorization.
