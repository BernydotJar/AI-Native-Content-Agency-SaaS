# 002 — Runtime Backup and Restore

Status: done
Owner: Data/Operations

## Problem

SQLite and PostgreSQL state are durable, but the active branch has no operator-grade backup artifact contract and no executed restore drill. A configured database or narrative runbook does not prove recoverability.

## Purpose

Provide fail-closed, verifiable backup and restore tooling for both supported persistence backends and execute ephemeral drills that preserve runs, audit events, sessions/rate-limit state, and memories.

## Actors and journeys

- **Operator:** creates a backup without exposing database credentials.
- **Incident responder:** verifies a manifest before restoring into an empty/approved target.
- **Auditor:** confirms checksum, integrity, row equivalence, command output, commit and limitations.
- **Release reviewer:** rejects release when a restore drill has not passed on the candidate code.

## Functional requirements

1. SQLite backup uses the SQLite backup API, not filesystem copy of a live WAL database.
2. SQLite backup and restored database pass `PRAGMA integrity_check`.
3. PostgreSQL backup uses custom-format `pg_dump` with owner/ACL exclusion.
4. Database URL secrets are passed through process environment, never command arguments or logs.
5. Every backup has a `agency-runtime-backup.v1` manifest with backend, timestamp, filename, bytes, SHA-256, validation result and tool metadata.
6. Restore verifies manifest schema, backend, size and checksum before mutation.
7. SQLite restore refuses an existing target unless `--replace` is explicit and uses atomic replacement.
8. PostgreSQL restore requires an empty target and uses one transaction where supported.
9. Tampered, truncated, wrong-backend or malformed backups fail closed.
10. Ephemeral SQLite and PostgreSQL restore drills compare representative row counts and runtime readability.

## Non-functional requirements

- Python standard library only for orchestration;
- PostgreSQL tools are explicit external prerequisites (`pg_dump`, `pg_restore`, `psql`);
- no raw URL/password is emitted;
- backup filenames are bounded and generated by the tool;
- temporary artifacts use restrictive permissions;
- errors are actionable and do not include secrets;
- production replacement remains human-gated.

## Invariants

- backup manifest checksum matches exact bytes;
- restore target is never silently overwritten;
- restore does not create/drop a PostgreSQL database;
- backup and restore commands never mutate the source;
- a successful drill proves data readability, not HA/failover or external object-storage durability.

## States and failures

`created -> verified -> restore_validated -> restored -> application_verified`

Terminal failures include source unavailable, invalid URL, missing tool, integrity failure, checksum mismatch, non-empty target, permission denied and restore command failure.

## Security/privacy/tenant boundaries

Backups contain tenant and identity-derived operational data and must be treated as sensitive. The tool does not encrypt; production storage must provide approved encryption, access control, retention and deletion. Manifests must not include raw credentials, tenant content, or database URLs.

## Acceptance criteria

- SQLite representative state survives backup/restore and all expected counts match;
- checksum tamper fails before target mutation;
- existing SQLite target is preserved without explicit replace;
- PostgreSQL migration fixture is dumped, restored into a new empty database, and count/schema equivalence passes;
- source and restore credentials do not appear in command output;
- documentation distinguishes ephemeral drill from production recovery;
- full backend/PostgreSQL and program gates pass.

## Out of scope

- cloud snapshot APIs;
- external object storage or KMS;
- automated deletion/retention;
- point-in-time recovery;
- cross-version schema downgrade;
- restoring persistent production data without explicit human authorization.
